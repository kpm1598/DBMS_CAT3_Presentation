The problem it solves

What is Transaction Management?

You send ₹500 to a friend. Your account is debited — and then the app crashes before your friend is credited. The money has vanished. Transaction Management is the part of the DBMS that makes sure this can never happen.

Your account
₹1,000 → ₹500
— ₹500 —➜
Friend's account
₹200 → ₹200
₹500 LOST

The debit succeeded, the credit never happened. The database is left inconsistent — ₹500 exists nowhere. This is exactly the failure a DBMS must prevent.

It manages

Every transaction from its start (begin) to its end — commit if all steps succeed, rollback if anything fails.

It protects

The database stays consistent even during crashes, power failures and many users working at the same time.

It guarantees

All or Nothing — a transaction's changes are either fully saved or fully undone. Never in between.

The unit of work

What is a Transaction?

A transaction is a single logical unit of work made of one or more database operations, executed together. Here is one ₹500 transfer, broken into its real steps:

  1. 1

    Begin

    The transaction starts. The DBMS notes: "a unit of work has begun — track everything from here."

    BEGIN TRANSACTION;
  2. 2

    Read your balance

    Fetch the current balance of your account from the database into memory.

    READ ( Your_Account ) → ₹1,000
  3. 3

    Debit ₹500

    Subtract the amount and write the new balance back.

    Your_Account = 1,000 − 500 → WRITE ₹500
  4. 4

    Credit ₹500

    Read your friend's balance, add the amount, write it back.

    Friend_Account = 200 + 500 → WRITE ₹700
  5. 5

    Commit

    Every step succeeded — so the DBMS saves all changes permanently, together.

    COMMIT;

If step 3 succeeds but step 4 fails, steps 1–3 are undone (rolled back) — the transaction counts as never having happened.

The Five Operations

Every transaction is built from these five basic operations on data. Tap each one to see what it does and where it appeared in our transfer.

The transfer used…

Read (both balances) and Write (both new balances). Insert, Update and Delete appear in other transactions — like opening an account, changing an address, or closing an account.

Read · R ( X )

Transfers the data item X from the database into a variable in memory so the transaction can work with it. Reading never changes the stored data.

In our example: READ ( Your_Account ) brought the balance ₹1,000 into memory — the very first thing the transfer did.

ACID Properties

Four guarantees that make a transaction trustworthy. Together they are the reason banks, railways and payment apps can trust a database with real money.

A · Atomicity

A transaction is treated as one indivisible atom — either all of its operations are completed, or none of them are. There is no middle state.

Example: ₹500 transfer — if the credit fails after the debit, the debit is rolled back. Your balance returns to exactly what it was.

Six States of a Transaction

From the moment a transaction begins to the moment it ends, it is always in exactly one of these six states.

→ → →
→ → also ends at Terminated
State 1 · Active

The transaction has begun and is executing its operations — reading and writing data. Every transaction starts here. Our transfer is Active while it debits and credits.

Success path

Active → Partially Committed → Committed → Terminated. All changes become permanent.

Failure path

Active → Failed → Aborted → Terminated. All changes are rolled back, as if nothing happened.

Wrap-up

All or Nothing — That's the Whole Idea

A transaction is one unit of work. It runs through six states, protected by the four ACID guarantees — and it either commits completely, or it rolls back completely. Nothing in between, ever.

Remember 1

Transaction = one logical unit of work: Begin → operations → Commit, or Rollback.

Remember 2

ACID = Atomicity, Consistency, Isolation, Durability — the four promises.

Remember 3

Six states, two roads: success ends at Committed, failure ends at Aborted. Both end at Terminated.
